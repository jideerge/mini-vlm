## 三、实验 A：特征形状与冻结

```text
输入图片 (8 张 VOC，尺寸各异)
  → CLIPProcessor          → pixel_values [8, 3, 224, 224]
  → CLIPVisionModel        → last_hidden_state [8, 50, 768]   ← 50 = 1 CLS + 49 patch
  → VisionEncoder(drop_cls) → [8, 49, 768]
```

| 项 | 值 |
| --- | --- |
| 视觉塔参数量 | 87,456,000（全部冻结） |
| 可训练参数 | **0** |
| 单图延迟 (bs=1) | 42.1 ms（含首次预热）/ 后段实测 11.67 ms |
| CLS 与 patch 平均余弦 | 0.1541 |
| patch 之间平均余弦 | 0.6394 |

**CLS 与 patch 相似度只有 0.154**，说明 CLS 是「全局汇聚」而非某个 patch 的复制品 —— 两者角色不同。
VLM 只需要 patch token（每个对应一个图像区域），所以 `drop_cls=True` 是正确默认值。

## 四、实验 A.3：预处理几何（本周最重要的发现）

### 问题

`CLIPProcessor` 到底把 500×375 的图变成什么？两种可能，后果完全不同：

- **拉伸**：整图压进 224×224，长宽比破坏，但内容不丢
- **缩放+中心裁剪**：最短边缩到 224，长边超出部分裁掉，**内容会丢**

配置里写着 `do_center_crop=True` 与 `size.shortest_edge=224`，字面上指向第二种，但**必须实测确认**。

### 实测方法

造「左半红、右半蓝」的 500×250（2:1）图，把分界放在宽度 10% / 50% / 90%，看输出 224 列里分界在哪：

| 分界位置 | 期望列(拉伸) | 期望列(裁剪) | 实测列 |
| :---: | :---: | :---: | :---: |
| 10% | 22 | −67（图外） | **无分界（整幅单色）** |
| 50% | 112 | 112 | **111** |
| 90% | 202 | 291（图外） | **无分界（整幅单色）** |

**平均误差：拉伸假设 149.7 列 vs 裁剪假设 0.3 列 → 判定为「缩放 + 中心裁剪」。**

关键证据：10% 那张图在输出里**找不到红蓝分界**，整幅变成单色 —— 红色那 10% 被裁掉了。
如果是拉伸，分界应该出现在第 22 列附近。

### 影响（必须在 Week 4/7 处理）

VOC 典型尺寸 500×375（4:3）：最短边 375 → 缩放 0.597 → 299×224 → 中心裁 224×224，
**左右各丢约 12.5%**。

- **计数 / 识别**：靠边的目标可能整个消失，与标注不一致
- **空间关系（左/右）**：被裁掉的一侧若正是目标所在，问题根本没法回答

### 解决方案（实测验证）

**推荐：预处理阶段先把图 pad 成正方形，再交给 processor。**

用「500×250 纯红图 pad 成 500×500（白底）」实测：

| 方案 | 输出里的白边 | 红色内容范围 |
| --- | :---: | :---: |
| 不 pad（默认中心裁剪） | **0 / 224 行**（全被裁掉） | 行 0–223（铺满） |
| pad-to-square | **112 / 224 行**（完整保留） | 行 56–167（居中） |

pad 后白边完整保留、内容居中且比例正确 —— **零丢失、零变形**。

另外两个方案及为何不首选：

- 只用画面中心的目标构造问答：从数据侧绕开，但浪费图像信息
- `do_center_crop=False`：保留全部内容但会变形，且实测其缩放行为**不是简单拉伸**
  （红蓝分界落在 44/223/402，而理论拉伸应为 22/112/201），行为不易预测

## 五、实验 B：逐层特征分析

取 16 张真实图片，记录 13 个 hidden state（索引 0 = patch embedding，1–12 = Transformer 层）。

变化量用**余弦距离** `1 − cos(h_l, h_{l−1})` 而非 L2 范数：最后一层输出会经过 `post_layernorm`
做整体缩放，L2 差值会被这个缩放污染。

| 层 | CLS 与最终层余弦 | 余弦距离 | patch 平均自相似度 |
| :---: | ---: | ---: | ---: |
| 0 (patch_emb) | −0.0041 | — | 0.2288 |
| 1 | 0.0347 | 0.2894 | 0.3339 |
| 2 | 0.0288 | **0.3834** | 0.2160 |
| 4 | 0.0343 | 0.2586 | 0.1976 |
| 8 | 0.1102 | 0.2696 | 0.2309 |
| 10 | 0.1460 | 0.2795 | 0.3579 |
| 11 | **0.2990** | 0.1728 | 0.3807 |
| 12 (最终) | 1.0000 | 0.3586 | **0.6395** |

**三条观察**：

1. **CLS 与最终层的相似度单调上升，但直到第 11 层也只有 0.299** —— 表示是逐层渐进改写的，
   没有哪一层能替代最后一层。这从工程上证明「取中间层省计算」在这里不成立。
2. **第 12 层余弦距离突然回升（0.3586）** —— 这是 `post_layernorm` 造成的，
   正是它让 L2 指标失真的原因。用余弦距离仍然能看到这个跳变，说明最后一层确实做了显著变换。
3. **patch 自相似度从 0.229 涨到 0.640** —— token 之间越来越像？
   注意这**不是**「表示分化」，而是深层表示共享了更多全局语义成分。
   浅层每个 patch 记录局部纹理（彼此差异大），深层则融入了整图语义（彼此趋同）。
   这是 VLM 能用 49 个 token 表达整幅图的原理。

> ⚠️ 上一版脚本把「最接近最终层的中间层」在包含最终层的范围里取最大值，结果恒为 12（自己比自己 = 1.0），
> 结论无意义。已修正为只在 **0..L−2** 范围内比较，得到 **11**（cos 0.299）。

## 六、实验 C：零样本验证（编码器真的看得懂吗）

样本：20 类 × 10 张 = 200 张 VOC **单类别**图片（整张图只有一个物体类别，保证问题有唯一答案）。

| 指标 | 值 |
| --- | ---: |
| **Top-1 准确率** | **86.50%** |
| **Top-5 准确率** | **97.50%** |
| 随机基线 Top-1 | 5.00%（1/20） |
| 相对随机基线 | **17.3×** |
| 编码耗时 | 1.66 s（120 img/s） |

**逐类表现**（两端）

| 最好 | Top-1 | 最差 | Top-1 |
| --- | ---: | --- | ---: |
| bird / boat / bus / car / diningtable / horse / motorbike / train | 100% | **chair** | **40%** |
| aeroplane / bicycle / cat / sheep | 90% | bottle / pottedplant / sofa | 70% |

`chair` 最差（40%）符合直觉：VOC 里椅子常与餐桌同框，且形态差异极大。

### 关于「置信度看起来很低」

上一版报告显示典型案例的置信度只有 0.051，看着像 bug。实测诊断后确认**不是 bug**，但**概率这个指标本身没有信息量**：

- `logit_scale = 100`，softmax 概率被整体缩放
- 20 个类别的余弦相似度本来就挤在 0.2–0.3 的窄区间：实测 **top1 余弦 = 0.2762**

所以概率接近均匀是正常现象。**尺度无关**的判断依据是余弦间隔：

```text
平均 top1 − top2 余弦间隔 = 0.0421
```

即模型确实有倾向（Top-1 86.5% 就是证据），只是倾向不强。
**报告里凡涉及 CLIP 置信度，一律用余弦间隔，不用 softmax 概率。**

## 七、实验 C2：kNN 验证（独立于文本的判别力证据）

只看图像特征、完全不用文本塔，5-NN + 余弦距离、5 折交叉验证：

> kNN 交叉验证准确率 **>80%**（20 类随机基线 5%）

这是对「视觉编码器有效」的**独立证据**：它不依赖 CLIP 的文本对齐，
说明图像特征本身已经把语义相近的图片聚在了一起。零样本 86.5% 里既包含视觉能力也包含文本对齐能力，
两者相互印证。

## 八、实验 D：数据增强敏感性

取 200 张真实图片，施加不同变换，测特征偏移（cos=1 表示完全不变）。

| 变换 | 投影后嵌入（全局语义） | patch 特征（空间细节） | 嵌入 L2 |
| --- | ---: | ---: | ---: |
| 原图 | 1.0000 | 1.0000 | 0 |
| 轻微颜色抖动 | 0.9898 | 0.9885 | 0.128 |
| **水平翻转** | **0.9861** | **0.7217** | 0.158 |
| 缩放到 50% 再回原尺寸 | 0.9527 | 0.9639 | 0.302 |
| 中心裁掉 20% | 0.9498 | 0.8001 | 0.308 |
| 旋转 10° | 0.9330 | 0.8072 | 0.359 |
| **中心裁掉 40%** | **0.9085** | **0.7113** | 0.419 |

**两条关键洞察**：

1. **翻转是特例**：全局语义几乎不变（0.986），但**空间细节剧烈变化**（0.722，全表最低之一）。
   原因很直观 —— 翻转后「左边的猫」变成了「右边的猫」。
   **这直接影响 Week 7 的空间关系实验：绝对不能对训练数据做随机水平翻转**，
   否则「在左边」的标注就会与画面矛盾，模型学到的空间概念会被毒化。
2. **裁剪破坏最大**：与第 4 节相互印证 —— 裁剪会改变画面的内容构成，
   而 CLIP 的预处理本身就在做中心裁剪，等于训练/推理时叠加了两次裁剪。

**由此确定的训练增强纪律**：只允许语义保持的增强（颜色抖动、轻微缩放）；
翻转与裁剪要么禁用，要么改变标注。本项目选择**禁用水平翻转**。

| 指标 | 值 |
| --- | ---: |
| 图片数 | 1000 |
| 总耗时 | **8.34 s** |
| 吞吐（batched） | 119.9 img/s |
| 单图延迟（bs=1） | **11.67 ms** |
| 批内单图均摊 | 2.57 ms |
| 显存峰值 | 685 MB |
| 磁盘占用 | **74.2 MB**（76 KB/图） |

缓存内容（三者维度不同，用途不同）：

| 张量 | 形状 | 用途 |
| --- | --- | --- |
| `patch_features` | `(1000, 49, 768)` fp16 | **VLM 的 Projector 吃这个**（投影前） |
| `cls_feature` | `(1000, 768)` fp16 | 视觉塔 CLS（投影前） |
| `image_embeds` | `(1000, 512)` fp16 | CLIP 投影后 + 归一化，检索/零样本用 |

**5 万张外推**：约 **7 分钟**，磁盘约 **3.62 GB**（与计划书估算的 3.8 GB 一致）。

⚠️ **一个必须记住的区分**：

- **VLM 用投影前的 768 维 patch 特征**（喂 Projector）
- **零样本/检索必须用投影后的 512 维归一化嵌入**（CLIP 的对比学习目标定义在这里）

两者混用会得到毫无意义的指标。这与 Week 1 笔记里「vision encoder 输出的 768 维」是同一件事的两个视角。

## 十一、对后续周次的三条硬约束

1. **Week 4 数据工程**：Dataset 里必须先 `pad_to_square` 再交给 CLIPProcessor，
   否则靠边目标会在标注与画面之间不一致（计数、空间关系都会被污染）。

3. **Week 5 训练管线**：直接用 `data/processed/features_w2` 这套缓存格式
   （`patch_features` / `cls_feature` / `image_embeds` + `index.json`），
   训练时不再加载 CLIP —— 这是省显存与提速的关键。
